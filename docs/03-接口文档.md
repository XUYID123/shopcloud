# 第一版 RESTful API 接口文档

本文与 [OpenAPI 文件](openapi.json) 配套使用，修订日期为 2026-10-15，契约版本为 1.2.0-partial。OpenAPI 包含请求/响应字段、必填项、类型、枚举和边界；本文说明业务语义与调用顺序。

POST /api/v1/users 已实现，当前直连地址 http://localhost:8081；User 使用 roles 数组以匹配 RBAC 关系。其余接口及网关/Nacos/Sentinel 链路仍按实施阶段完成。目标网关开发地址为 http://localhost:8080，生产入口使用 HTTPS。注册运行与测试见 [09 文档](09-用户注册实现与验收.md)。

## 1. 通用约定

- 外部业务路径 `/api/v1`；管理路径 `/api/v1/admin`；内部 `/internal/v1`，禁止网关透传；支付回调 `/callbacks/payments/{provider}`。
- 业务 JSON 使用 UTF-8、camelCase；ID/订单号/支付号使用字符串；金额为整数分且 currency 固定 CNY；重量为整数克；数量为整数袋。
- 时间如 `2026-10-13T10:00:00+08:00`；生产/到期日期用 `YYYY-MM-DD`。
- 鉴权头 `Authorization: Bearer <accessToken>`；管理端必须 ADMIN；普通用户只能访问自己的地址/购物车/订单/支付单。
- 请求可传 `X-Request-Id`（安全字符、最长 64）；服务生成/传播 traceId，响应头返回 `X-Request-Id`，返回体含 traceId。
- 高风险写请求传 `Idempotency-Key`（16–128 位可打印安全字符串，推荐 UUID）：下单、创建支付、取消、收货、入库、库存调整、发货、Mock 成功触发。PUT/DELETE 的绝对状态操作本身幂等。幂等键作用域包含身份、method 和路径。
- 相同 key + 相同请求返回同一资源的当前结果；相同 key + 不同内容返回 409 `IDEMPOTENCY_CONFLICT`。并发未完成返回 409 `REQUEST_IN_PROGRESS`；使用同一 key 重试。订单绑定及报价单消费约束长期保留，其余命令记录第一版也不清理。
- 列表默认 page=1、size=20、size≤50；订单列表用 cursor（不可解析的分页游标）+size，按 createdAt/id 降序，避免深分页。商品排序只接受预置枚举。

**RESTful 资源规范**：URI 使用名词与子资源；GET 只读，POST 创建集合中的资源，PUT 完整更新指定资源/单例子资源，DELETE 删除资源或撤销会话。修改一个属性时定义独立子资源，例如 sale-status，不用 PUT 整个商品来仅改一项，也不开放客户端任意设置订单状态。业务查询不能用 GET 执行扣库、支付或收货。

注册是创建 users，登录是创建 auth/sessions，退出是删除当前 session；刷新是 POST auth/token-refreshes 的令牌交换资源，返回 200 新凭证，不能重复消费旧 refreshToken。取消是创建 cancellations 子资源，收货是 PUT receipt 单例子资源，Mock 成功是创建 payment-events。支付渠道回调是外部协议接收端，遵守签名与 ACK 协议。

同步创建通常返回 201；异步创建订单/取消申请返回 202，并用 Location 指向已持久化且可 GET 查询的资源。幂等重试可返回 200 和同一资源，不再创建第二条记录。用户与管理端的 PUT 请求是指定资源的完整表示，version/expectedVersion 用于并发控制。

成功业务响应（HTTP 200/201/202）：

```json
{
  "code": "OK",
  "message": "成功",
  "data": {"orderNo": "019a-order-001", "orderStatus": "PREPARING"},
  "traceId": "req-demo-001"
}
```

失败响应使用对应 HTTP 状态，不能把所有错误都包装成 HTTP 200：

```json
{
  "code": "STOCK_NOT_ENOUGH",
  "message": "所选规格库存不足",
  "data": null,
  "traceId": "req-demo-001"
}
```

| HTTP | code 示例 | 含义/处理 |
|---:|---|---|
| 400 | VALIDATION_ERROR / BAD_CALLBACK | 参数、格式、签名或回调字段不正确 |
| 401 | UNAUTHORIZED / TOKEN_EXPIRED | 登录/刷新凭证失效 |
| 403 | FORBIDDEN | 缺少管理员或内部调用权限 |
| 404 | NOT_FOUND | 资源不存在；用户请求他人的资源也返回此值 |
| 405 / 415 | METHOD_NOT_ALLOWED / UNSUPPORTED_MEDIA_TYPE | 请求方法或内容类型不支持 |
| 409 | USERNAME_EXISTS | 用户名已注册；包含大小写不同但判定相同的用户名 |
| 409 | IDEMPOTENCY_CONFLICT / REQUEST_IN_PROGRESS / STATE_CONFLICT | 幂等冲突、并发处理中、状态不允许 |
| 409 | PRICE_CHANGED / QUOTE_EXPIRED / QUOTE_USED | 重新结算；QUOTE_USED 可提示已有订单 |
| 422 | STOCK_NOT_ENOUGH / PRODUCT_UNAVAILABLE / DELIVERY_UNSUPPORTED / ORDER_LIMIT_EXCEEDED / WEIGHT_LIMIT_EXCEEDED / BATCH_UNAVAILABLE | 业务限制；异步缺货反映在订单 FAILED.failureCode 中 |
| 429 | RATE_LIMITED | 按 Retry-After 等待后重试 |
| 503 | CIRCUIT_OPEN / DEPENDENCY_UNAVAILABLE / RULES_NOT_READY | Sentinel 熔断、依赖故障或关键规则未就绪；保留幂等键查询/重试，不得直接判断前一次没有成功 |
| 500 | INTERNAL_ERROR | 未知系统异常，仅返回通用提示；详细异常记录于服务端 |

DELETE/退出成功返回 200 + data=null，符合“带响应表示的删除”语义；第一版保持统一包裹，不使用 204。Sentinel 网关拒绝、MVC 拒绝和业务 blockHandler 均采用上面的错误结构，流控 429 附 Retry-After，熔断 503 不伪造成功。支付回调使用渠道规定的原始 ACK，Mock 为 `{ "code": "SUCCESS" }`，不使用业务包裹。

## 2. 用户与地址

| 方法/路径 | 权限 | 请求/关键规则 | data / HTTP |
|---|---|---|---|
| POST `/api/v1/users` | 公开，已实现 | username、password；username 3–32 位字母/数字/下划线且不区分大小写判重，密码 8–72 位 ASCII 可打印非空白字符；其他字段包括 role/roles/permissionIds/status 一律拒绝；服务端默认关联 USER | User / 201，Location 标识新用户资源 |
| POST `/api/v1/auth/sessions` | 公开 | username、password；创建登录会话；账号/IP 限流，失败统一提示 | TokenPair / 201 |
| GET `/api/v1/auth/sessions/current` | USER/ADMIN | 查询 token 中 sid 对应的当前会话 | AuthSession / 200 |
| POST `/api/v1/auth/token-refreshes` | refreshToken | refreshToken；轮换、过期和重用检测；客户端串行刷新 | TokenPair / 200 |
| DELETE `/api/v1/auth/sessions/current` | USER/ADMIN | 撤销当前 sid 会话，后续 token 无效 | null / 200 |
| GET `/api/v1/users/me` | USER/ADMIN | 取 token 中身份 | User / 200 |
| GET `/api/v1/addresses` | USER/ADMIN | 只取本人地址，最多 20 条 | Address[] / 200 |
| POST `/api/v1/addresses` | USER/ADMIN | receiver、phone、regionCode、detail、isDefault | Address / 201 |
| PUT `/api/v1/addresses/{addressId}` | 所有者 | 同上，完整替换；默认地址更新串行化 | Address / 200 |
| DELETE `/api/v1/addresses/{addressId}` | 所有者 | 已下单快照保留 | null / 200 |

TokenPair 包含 sessionId、accessToken、refreshToken、tokenType=Bearer、expiresIn=900（秒）、user。AuthSession 包含 sessionId、userId、createdAt、expiresAt（会话期限）。登录响应 Location 指向 `/api/v1/auth/sessions/current`；身份由返回 token 确定。调试阶段 JSON refreshToken 不建议存浏览器长期 localStorage；生产浏览器适配使用安全 cookie，接口契约届时单独版本化。

地址例：

```json
{
  "receiver": "张先生",
  "phone": "13800000000",
  "regionCode": "310115",
  "detail": "演示路100号",
  "isDefault": true
}
```

regionCode 是末级行政区代码，由服务端白名单映射完整地区；开发示例 `310115`，配送是否支持仍由运费规则判断。User 只返回 userId、username、roles，不返回密码 hash。roles 为角色编码数组，注册时为 ["USER"]。Location 的 /api/v1/users/{id} 是资源标识，当前未开放按 ID 查询用户的 GET 接口。

| GET `/api/v1/skus/{skuId}` | 公开，已实现 | 仅显示启用 SKU、已上架商品及启用分类，隐蔽状态统一 404 / SKU_NOT_FOUND | Sku，estimatedAvailable=null |

## 4. 结算与订单

| 方法/路径 | 权限 | 请求/用途 | HTTP / data |
|---|---|---|---|
| POST `/api/v1/checkout/quotes` | USER/ADMIN | addressId、items（1–20 个互不重复 skuId/quantity）；报价有效 5 分钟 | 201 / Quote |
| POST `/api/v1/orders` | USER/ADMIN + 幂等键 | quoteId；报价复核，异步锁库存 | 202（PREPARING）或重试终态 200 / Order |
| GET `/api/v1/orders` | USER/ADMIN | status?、cursor?、size≤50；本人订单 | 200 / OrderCursorPage |
| GET `/api/v1/orders/{orderNo}` | 所有者 | 三种状态、金额/地址/商品快照、物流、异常信息 | 200 / Order |
| POST `/api/v1/orders/{orderNo}/cancellations` | 所有者 + 幂等键 | reason 可选 ≤200；仅 PREPARING/UNPAID；创建取消申请，订单进入 CLOSING | 202 新建 / 200 重复 / Cancellation |
| GET `/api/v1/orders/{orderNo}/cancellations/{cancellationNo}` | 所有者 | 查询取消申请处理结果；与订单状态一起查看 | 200 / Cancellation |
| PUT `/api/v1/orders/{orderNo}/receipt` | 所有者 + 幂等键 | `{ "received": true }`；仅 SHIPPED；重复确认返回原确认记录 | 200 / Receipt |

创建订单响应头 `Location: /api/v1/orders/{orderNo}`。前端以 Order 的状态确定后续动作；不能在收到 202 后立即支付。异步缺货时 GET 仍 HTTP 200，orderStatus=FAILED、failureCode=STOCK_NOT_ENOUGH。

取消响应 Location 指向 `/api/v1/orders/{orderNo}/cancellations/{cancellationNo}`。Cancellation 包含 cancellationNo、orderNo、status=PENDING/SUCCEEDED/REJECTED、reason、requestedAt、completedAt、failureCode、orderUri。PENDING 对应关闭处理中；渠道确认关闭后 SUCCEEDED；支付竞争中已收款则 REJECTED，并按订单 PAID 流程处理。每个订单只创建一份用户取消申请；已经超时关闭但没有该申请的新取消请求返回 409，客户端查看订单即可。

Receipt 包含 orderNo、received=true、receivedAt（服务端时间）。PUT receipt 不允许客户端提交任意订单状态或收货时间，服务端保存确认时间并把订单转 COMPLETED；重复请求保持原 receivedAt。

取消申请示例：

```http
POST /api/v1/orders/019a-order-001/cancellations
Authorization: Bearer <accessToken>
Idempotency-Key: 20e5f6a0-01b8-4e71-8f26-1a33bba6b065
Content-Type: application/json

{"reason":"暂时不需要"}
```

响应 HTTP 202，Location 为 `/api/v1/orders/019a-order-001/cancellations/019a-cancel-001`，data 示例：

```json
{
  "cancellationNo": "019a-cancel-001",
  "orderNo": "019a-order-001",
  "status": "PENDING",
  "reason": "暂时不需要",
  "requestedAt": "2026-10-14T10:00:00+08:00",
  "completedAt": null,
  "failureCode": null,
  "orderUri": "/api/v1/orders/019a-order-001"
}
```

## 5. 支付与回调

| 方法/路径 | 权限 | 请求/规则 | HTTP / data |
|---|---|---|---|
| POST `/api/v1/payment-sessions` | 所有者 + 幂等键 | `{ "orderNo": "...", "provider": "MOCK" }`；只允许有效 UNPAID 订单，金额由内部查询 | 201 新建 / 200 重复 / PaymentSession |
| GET `/api/v1/payment-sessions/{paymentNo}` | 所有者 | 查询本服务状态；渠道补偿后台查单 | 200 / PaymentSession |
| POST `/callbacks/payments/{provider}` | 渠道签名 | 第一版 provider=MOCK，见下文；验签并耐久保存后 ACK | 200 / CallbackAck |
| POST `/api/v1/test/payment-sessions/{paymentNo}/payment-events` | dev/test + ADMIN + 幂等键 | `{ "type": "SUCCEEDED" }`；创建 Mock 支付事件，自动产生签名回调，正常 Outbox 流程 | 201 新建 / 200 重复 / MockPaymentEvent |
| GET `/api/v1/test/payment-sessions/{paymentNo}/payment-events/{eventId}` | dev/test + ADMIN | 查询对应 Mock 渠道事件；支付/订单落账进度另查支付单/订单 | 200 / MockPaymentEvent |

PaymentSession 字段：paymentNo、orderNo、provider、status、amountFen、currency、expiresAt、clientParams。Mock 的 clientParams 只有 `mockPaymentNo`，真实渠道的 clientParams 需独立适配。MockPaymentEvent 为 eventId、paymentNo、type=SUCCEEDED、createdAt；创建响应 Location 指向事件查询资源。模拟事件在 production profile 不注册，返回 404，事件创建不等于订单已经 PAID。

Mock 适配器先耐久保存渠道事件，查单读取这份渠道事实，之后可靠投递签名回调。不能因为回调尚未送达，就在关闭竞争时把渠道判定为未支付；重复创建事件受幂等键和唯一成功事实约束。

Mock 回调 body：

```json
{
  "eventId": "mock-event-001",
  "paymentNo": "019a-payment-001",
  "providerTransactionNo": "mock-txn-001",
  "merchantId": "flour-dev",
  "amountFen": 7400,
  "currency": "CNY",
  "status": "SUCCEEDED",
  "paidAt": "2026-10-13T10:02:00+08:00"
}
```

Mock 请求头 `X-Mock-Timestamp`（Unix 秒）、`X-Mock-Nonce`、`X-Mock-Signature`。签名为 Base64(HMAC-SHA256(secret, timestamp + "\n" + nonce + "\n" + **原始 body 字节** + "\n"))，时间偏差最多 300 秒，常量时间比较。商户、金额、币种、支付号必须匹配持久化支付记录；eventId 与 providerTransactionNo 唯一约束防重。

对合法重复 eventId + 相同 payload hash 返回 ACK，不重复业务执行；同 eventId 不同 payload 返回 BAD_CALLBACK 并告警。时间窗口外的补偿使用主动查单，不靠重放旧签名绕过校验。nonce 关联 eventId/payload hash，窗口内相同合法请求可重复 ACK，未知或不同内容的 nonce 重用拒绝。

这是**本项目 Mock 协议**。真实微信/支付宝必须替换验签/解密/证书更新/应答/查单/关单/退款规则，不能使用 Mock 签名接收真实资金回调。前端跳转结果不作为入账依据。

| GET `/api/v1/admin/orders` | status?、cursor?、size；可选 orderNo 精确查询 | 200 / OrderCursorPage |
| GET `/api/v1/admin/orders/{orderNo}` | 任意用户订单详情 | 200 / Order |
| POST `/api/v1/admin/orders/{orderNo}/shipments` | 幂等键；carrierCode、trackingNo；只能 PAID + CONFIRMED 且批次可出库 | 201 新建 / 200 重复 / Order |

产品/SKU 更新采用 expectedVersion 防止后台互相覆盖。历史订单价格不跟随更新。库存初始为 0，通过批次入库增加；管理端不能直接覆盖库存总数。

## 7. 内部同步接口

这些接口定义在 OpenAPI 中用于联调，必须直连服务端口且携带 `X-Service-Token`；生产替换为服务身份凭证。令牌绑定调用者/audience/scope，不能所有服务共用一个无限权限口令。内部查询的 userId 来自已经验证的会话，校验资源归属。

| 方法/路径 | 服务/权限 | 请求/响应 |
|---|---|---|
| GET `/internal/v1/users/addresses/{addressId}?userId=...` | user，order:address:read | Address；归属不匹配 404 |
| POST `/internal/v1/products/quotes` | product，order:product:quote | items[]；从权威数据读取，ProductQuote.lines 含 skuId/name/spec/weight/price/version；不可售 422 |
| GET `/internal/v1/inventory/reservations/{orderNo}` | inventory，order:inventory:read | Reservation：state、items/分配批次、failureCode |
| GET `/internal/v1/inventory/reservations/{orderNo}/allocation` | inventory，order:inventory:read | Allocation：可发货标志、批次明细及状态；用于发货/补偿 |
| GET `/internal/v1/orders/{orderNo}/payment-context?userId=...` | order，payment:order:read | PaymentContext：orderNo/userId/amount/currency/orderStatus/expiresAt；只读，不代替支付服务关闭墓碑校验 |
| GET `/internal/v1/payments/orders/{orderNo}` | payment，order:payment:read | PaymentControlView：state、paymentStatus、paymentNo、amount、closeRequested、refundStatus；补偿核验 |

库存预占/确认/释放和支付关闭/退款采用事件驱动命令，不额外暴露一个绕过编排的公共库存扣减接口。查询必须能读取权威写节点，不依赖可能滞后的展示缓存。

## 8. 事件协议

交换机 `flour.business.v1`（topic，持久化），每个消费业务单独建队列。初始三个业务队列：`flour.inventory.commands.v1`、`flour.order.results.v1`、`flour.payment.commands.v1`，各自有 retry/DLQ。商品缓存失效另外建广播订阅队列，不和交易竞争。

```json
{
  "eventId": "019a-event-001",
  "eventType": "InventoryReserveRequested",
  "schemaVersion": 1,
  "aggregateId": "019a-order-001",
  "aggregateVersion": 1,
  "occurredAt": "2026-10-13T10:00:00+08:00",
  "traceId": "req-demo-001",
  "payload": {
    "orderNo": "019a-order-001",
    "warehouseId": "WH-SH-01",
    "items": [{"skuId": "2001", "quantity": 2}]
  }
}
```

| 事件 / routingKey | 生产者 → 消费者 | payload 必需内容 |
|---|---|---|
| InventoryReserveRequested / inventory.reserve.requested | order → inventory | orderNo、warehouseId、items(skuId,quantity)、requestHash |
| InventoryReserved / inventory.reserved | inventory → order | orderNo、reservationState=RESERVED、allocations(skuId,batchId,batchNo,quantity) |
| InventoryRejected / inventory.rejected | inventory → order | orderNo、failureCode（STOCK_NOT_ENOUGH/BATCH_UNAVAILABLE）、failedSkuIds |
| InventoryConfirmRequested / inventory.confirm.requested | order → inventory | orderNo、paymentNo |
| InventoryConfirmed / inventory.confirmed | inventory → order | orderNo、reservationState=CONFIRMED |
| InventoryReleaseRequested / inventory.release.requested | order → inventory | orderNo、reason |
| InventoryReleased / inventory.released | inventory → order | orderNo、reservationState=RELEASED |
| InventoryOperationRejected / inventory.operation.rejected | inventory → order | orderNo、operation、actualState、failureCode；例如 Confirm 已释放预占 |
| PaymentSucceeded / payment.succeeded | payment → order | orderNo、paymentNo、providerTransactionNo、amountFen、currency、paidAt |
| PaymentCloseRequested / payment.close.requested | order → payment | orderNo、userId、amountFen、currency、reason；无支付记录也能创建墓碑 |
| PaymentClosed / payment.closed | payment → order | orderNo、paymentNo（可 null）、channelState=CLOSED |
| PaymentRefundRequested / payment.refund.requested | order → payment | orderNo、paymentNo、refundNo、amountFen、reason=LATE_PAYMENT/INVENTORY_EXCEPTION |
| PaymentRefundSucceeded / payment.refund.succeeded | payment → order | orderNo、paymentNo、refundNo、amountFen、refundedAt |
| PaymentRefundFailed / payment.refund.failed | payment → order | orderNo、paymentNo、refundNo、failureCode；查单确认失败或达到人工阈值 |
| ProductChanged / product.changed | product → 缓存订阅 | productId、skuIds、version |

HTTP OpenAPI 不代表 RabbitMQ 消息 schema；上表是第一版消息字段契约，编码时给每一种事件定义 DTO 和兼容性测试。示例为精简演示，正式 InventoryReserveRequested 还必须含 requestHash。

eventId 防同消息重复，业务 orderNo/operationNo 防同命令不同消息 ID 重复。不能只比较 aggregateVersion 来丢弃全部旧消息：生产者不同、版本流不同；最终以本地业务状态和操作约束判定。Outbox/消费去重与业务状态更新在同一数据库事务中，ACK 在提交之后。

## 9. 跑通一笔交易的调用顺序

管理员初始化分类 → 商品（下架）→ SKU → 批次入库 → PUT sale-status 上架。POST users 注册 → POST auth/sessions 登录 → 添加上海支持地址 → 查看商品 → 设置购物车 → 结算报价 → 带唯一幂等键下单 → 查询到 UNPAID → 创建 MOCK 支付 → 管理员在 dev/test POST payment-events 创建成功事件 → 查询到 PAID/CONFIRMED → 管理员创建 shipment 发货 → 用户 PUT receipt 确认收货。

另一条必须演示的流程：下单 → UNPAID → POST cancellations（或系统到期触发关闭）→ CLOSING → 支付关单确认 → CLOSED → RELEASED；用户取消通过 Location 查询 Cancellation 到 SUCCEEDED。压测与故障验收再验证重复请求、缺货、晚到支付、乱序消息和 MQ 恢复。
