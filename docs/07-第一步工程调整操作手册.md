# 第一步：让 shop-user 正确引用 shop-common

日期：2026-10-15。本文为工程调整教程。当前实际代码与运行步骤以 08/09 文档为准；本文的 common 自动配置示例仍是供手动操作的方案，用户服务当前通过已有 @Import 加载共享处理器。

后续调整：按当前需求，shop-user 保留 Compose 依赖，在启动时自动启动 MySQL 并执行 Flyway。本文“从 user 移除 Compose 依赖”的早期步骤不再采用；数据库配置与运行方式以 [08 操作说明](08-Docker数据库与Flyway启动.md) 为准。common 的公共响应和异常处理职责不变。

对应开发清单的第一项“修正模块配置”。完成后的关系是：shop-user 是启动的业务服务，shop-common 是提供统一响应和共享全局异常处理的普通 JAR。各业务服务引用并加载 common 中的处理器，不复制实现。注册接口的建表、密码哈希和业务代码属于下一项。

本操作先保留当前 JDK 17 / Boot 3.2.5，避免同时重构模块和升级框架。现有架构文档的目标版本统一仍是正式接入 Nacos/Sentinel 前的任务，不把本次结果当作完整微服务基线已完成。

## 操作 1：修正用户模块自己的 artifactId

在 IDEA 左侧 Project 找到 shop-user/pom.xml。

保持 parent 中的 com.dong / shop / 1.0-SNAPSHOT 不变，仅把 parent 结束标签后面的模块名：

```xml
<artifactId>shop-common</artifactId>
```

改为：

```xml
<artifactId>shop-user</artifactId>
```

artifactId 是 Maven 模块坐标的一部分，与 spring.application.name 的作用不同。文件夹叫 shop-user，并不会自动纠正 POM 中的模块名。

检查：common 和 user 的 artifactId 分别为 shop-common、shop-user，不能相同。

## 操作 2：保留 common 的共享异常处理，仅移动测试接口

GlobalExceptionHandler 和 Result 都保留在 common 中，它们是其他服务复用的公共能力。仅将 TestController 移到 user；在 IDEA 中通过 Refactor → Move 移动，检查 package 和 import 是否正确。

| 原文件 | 操作 | 目标 package |
|---|---|---|
| shop-common/src/main/java/org/spring/shopcommon/controller/TestController.java | 移到 shop-user/src/main/java/org/spring/shopuser/controller/TestController.java | org.spring.shopuser.controller |
| shop-common/src/main/java/org/spring/shopcommon/result/GlobalExceptionHandler.java | 保留原位置 | org.spring.shopcommon.result |

TestController 导入公共响应类：

```java
import org.spring.shopcommon.result.Result;
```

GlobalExceptionHandler 与 Result 仍在 common 的同一个包中，无需额外 import。

ShopUserApplication 当前在 org.spring.shopuser 包下，只会默认扫描它及其子包，不能默认扫描兄弟包 org.spring.shopcommon。操作 5 中在 common 内提供自动配置，业务服务引用依赖即可加载共享处理器，无需修改启动类。

检查：测试接口属于 user，共享异常处理实现属于 common。

## 操作 3：移除 common 的应用入口

下列两个文件是现有脚手架的启动类及其启动测试，common 改成普通库后将它们移除：

```text
shop-common/src/main/java/org/spring/shopcommon/ShopCommonApplication.java
shop-common/src/test/java/org/spring/shopcommon/ShopCommonApplicationTests.java
```

保留 shop-user 的 ShopUserApplication 和 ShopUserApplicationTests。以后 common 可以编写普通单元测试，但这里不再启动一个 Spring Boot 应用上下文。

common 原有 application.properties 与 compose.yaml 在它变成库后不再作为应用配置使用。将 Compose 示例移到 infra/compose.yaml；不要在这一步执行它来创建数据库，数据库初始化另做。

移除 common 的 application.properties，尤其不能把它作为公共资源带进业务服务，影响应用名。IDEA 中旧的 ShopCommonApplication 运行配置也可以移除，后续运行 ShopUserApplication。

检查：common 此时保留 Result 和 GlobalExceptionHandler 等公共代码；user 保留自己的启动入口。

## 操作 4：将 common 的 POM 精简为普通 JAR

将 shop-common/pom.xml 调整为以下内容。保留你现有根 POM 的版本管理，不重复声明框架版本：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>com.dong</groupId>
        <artifactId>shop</artifactId>
        <version>1.0-SNAPSHOT</version>
        <relativePath>../pom.xml</relativePath>
    </parent>

    <artifactId>shop-common</artifactId>
    <packaging>jar</packaging>

    <dependencies>
        <!-- common 编译共享 MVC 处理器；使用方自行声明所需 Web 技术栈 -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
            <optional>true</optional>
        </dependency>
        <dependency>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
            <optional>true</optional>
        </dependency>
    </dependencies>
</project>
```

当前 Result 使用 Lombok 的 @Data，GlobalExceptionHandler 使用 Spring Web 注解和日志，因此保留 Lombok 与可选 Web starter。optional=true 表示 Web starter 不会作为 common 的传递依赖强加给所有使用方；MVC 业务服务仍声明自己的 Web starter。common 不需要数据库驱动、Compose starter 或 Boot 打包插件。后续依赖精简时可替换为按需的 Spring Web/日志依赖，本次优先保持操作清晰。

再打开 common 的 Result.java，删除没有使用的 Spring import：

```java
import org.springframework.context.annotation.Bean;
```

本次暂时保留 Result 的现有字段和方法，避免将工程调整与接口响应格式调整混在一起。注册开发时再统一字符串业务码、traceId 和实际 HTTP 状态。

检查：common 有编译共享处理器所需依赖，但没有 Spring Boot 启动类和插件；普通 JAR 可以包含 Spring 组件。

## 操作 5：给用户服务添加 common 依赖

在 shop-user/pom.xml 的 dependencies 内增加：

```xml
<dependency>
    <groupId>com.dong</groupId>
    <artifactId>shop-common</artifactId>
    <version>${project.version}</version>
</dependency>
```

这里的 ${project.version} 当前继承为 1.0-SNAPSHOT，与 common 一致。依赖关系是 user → common；不要在 common 中反过来引用 user。

shop-user 保留自身的 Web starter、Lombok、测试依赖；MySQL 驱动可保留，后续建表与数据访问阶段使用。仅有 MySQL 驱动并不等于已经配置数据源。

从 user 中移除 spring-boot-docker-compose 依赖。基础设施之后从 infra 单独启动，避免启动用户服务时再次报找不到 Compose 文件。

由于根项目导入的是 Boot BOM，没有继承 Boot starter parent，现有 Boot Maven 插件需要显式锁定版本：

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <version>${spring-boot.version}</version>
</plugin>
```

该插件在本步骤用于固定版本；IDE 启动不依赖它。后续如果需要 java -jar 部署，再按完整构建任务配置 repackage execution 并验证可执行 JAR，不能把普通 package 成功等同于可执行包已完成。

在 common 中注册自动配置，让使用方只添加 Maven 依赖即可启用。新建 shop-common/src/main/java/org/spring/shopcommon/autoconfigure/CommonWebAutoConfiguration.java：

```java
package org.spring.shopcommon.autoconfigure;

import org.spring.shopcommon.result.GlobalExceptionHandler;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnWebApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.web.servlet.DispatcherServlet;

@AutoConfiguration
@ConditionalOnClass(DispatcherServlet.class)
@ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
public class CommonWebAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(GlobalExceptionHandler.class)
    public GlobalExceptionHandler globalExceptionHandler() {
        return new GlobalExceptionHandler();
    }
}
```

保留 GlobalExceptionHandler 上的 @RestControllerAdvice。在 common 的 resources 中新建以下纯文本文件，注意文件名没有 .txt 后缀：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

内容只有一行全限定类名：

```text
org.spring.shopcommon.autoconfigure.CommonWebAutoConfiguration
```

Boot 3 会读取依赖 JAR 内的这个文件并加载自动配置，见 [Spring Boot 3.2.5 官方说明](https://docs.spring.io/spring-boot/docs/3.2.5/reference/html/features.html#features.developing-auto-configuration.locating-auto-configuration-candidates)。只在 common 写 @Configuration 或 @RestControllerAdvice 而没有扫描/自动配置入口，不保证它会被 user 加载。

后续 product、order 等 MVC 服务引用 common 即可，不必逐个加 @Import。已加的 @Import(GlobalExceptionHandler.class) 可以移除，统一采用自动配置路径，也不要扩大组件扫描到 common 的自动配置包。@ConditionalOnMissingBean 在已有同类型处理器时回退；这不代表它能检测所有其他类型的 Advice 是否有业务冲突。

每个服务进程拥有自己的处理器实例，处理本服务 MVC 请求的异常；它不会跨网络捕获另一个服务的异常。Servlet 与 DispatcherServlet 条件限制此配置只在 MVC 服务启用；WebFlux 网关采用自己的响应式异常机制，共享响应类型和错误码即可。前提是 common 的 Web starter 按上文设置为 optional，网关不会因此被强加 MVC 依赖。

检查：user 中的 Result 引用可以解析；自动配置类与 imports 文件都进入 common 构建产物；只引用 common 即可在 user 容器中获得一个共享处理器 Bean，common 没有 user 依赖。

## 操作 6：检查聚合模块和应用配置

根 pom.xml 已经登记了以下两个模块，当前无需重复添加：

```xml
<modules>
    <module>shop-common</module>
    <module>shop-user</module>
</modules>
```

将 shop-user/src/main/resources/application.properties 设置为：

```properties
spring.application.name=shop-user
server.port=8081
```

当前没有加入 JDBC/MyBatis starter，本步骤不用虚构数据库连接信息。其他服务先不运行，避免被无关模块的版本与依赖问题干扰。

检查：端口为 8081，应用名为 shop-user，common 不提供应用配置。

## 操作 7：在 IDEA 中重新加载并编译

1. 保存修改，在右侧 Maven 面板点击 Reload All Maven Projects。
2. 展开根项目，确认能够区分 shop-common、shop-user；user 的 Dependencies 中出现 com.dong:shop-common:1.0-SNAPSHOT。
3. 在 File → Project Structure 检查两个模块使用当前 JDK 17。
4. 在 Settings → Build, Execution, Deployment → Compiler → Annotation Processors 中确认 Lombok 注解处理启用；若已有正常配置则保持。
5. 从 Build 菜单执行 Build Project。若出现 Result 找不到或 setCode 等方法缺失，先处理依赖加载、包名或 Lombok 问题，再启动。

本机曾遇到 Maven Wrapper 自身的 Windows 脚本错误，这与 IDE 运行 main 是不同路径。本次优先使用 IDEA 现有的 Maven 导入与构建能力；若 IDEA 配置为 Wrapper 且导入报相同脚本错误，可在 Maven 设置选择 Bundled Maven，并重新加载。

检查：这两个模块编译通过，没有重复模块坐标或缺失公共类错误。

## 操作 8：启动用户服务，验证 common 被实际引用

打开 shop-user 的 ShopUserApplication，点击 main 方法旁的运行按钮。运行配置的 module 应为 shop-user，main class 应为 org.spring.shopuser.ShopUserApplication。

检查启动日志出现 Started ShopUserApplication，HTTP 端口是 8081。

当前已实现注册，可打开 shop-user/requests/user-registration.http，或用接口工具发出：

```http
POST http://localhost:8081/api/v1/users
Content-Type: application/json

{"username":"flour_demo_01","password":"FlourDemo123!"}
```

第一次注册预期 HTTP 201，示例响应如下；已有同名用户时为 409，换一个用户名即可验证新注册：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {"userId":"1001","username":"flour_demo_01","roles":["USER"]},
  "traceId": "req-demo-001"
}
```

响应由 user 中的 Controller 调用 common 中的 Result 构造，说明公共响应引用已生效；ID 和 traceId 以实际响应为准。非法注册请求返回 400，重名返回 409，经 common 的共享处理器生成统一错误。当前注册与数据库集成已经验证，具体代码和测试见 09 文档。Nacos/Sentinel 按后续阶段接入。

## 操作 9：本步骤完成后再进入注册开发

按以下任务逐项推进，不在本步骤同时完成：

| 下一项 | 具体操作 | 完成标准 |
|---|---|---|
| 公共响应与异常 | Result 改为契约字段；增加 ErrorCode、BusinessException；完善 common 中的共享异常处理器并通过 common 自动配置加载 | 参数错误 400，唯一冲突 409，未知异常 500；不向客户端暴露异常原文 |
| 用户表与连接 | 配置真实 MySQL 地址/账号与环境变量，加入数据访问和迁移依赖，创建 user_account 迁移与唯一索引 | 启动连接成功，迁移可重复运行，用户名唯一约束生效 |
| Entity 与 Mapper | 新建 UserEntity、UserMapper，实现按用户名查询与插入，返回自增 ID | 数据真正落到 MySQL，字段与数据设计一致 |
| 注册输入输出 | UserRegisterRequest 校验 username/password；UserVO 只返回 userId/username/roles | 不接收管理员角色，不返回密码哈希；当前实现见 09 文档 |
| 注册业务 | UserService 使用 BCrypt、默认 USER、处理并发唯一冲突 | 数据库保存哈希，相同用户名并发只成功一次 |
| RESTful 接口 | UserController 提供 POST /api/v1/users，返回 201 与 Location | 合法注册 201，非法参数 400，重复用户名 409 |

Nacos、Sentinel 与网关的实际接入仍按 06 文档安排在首轮完成；上面的 8081 直连只是便于定位每个开发任务，不代表最终对外入口。
