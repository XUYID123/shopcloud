# 业务异常码与访问日志统一

实现日期：2026-11-02。响应 JSON 协议不变，补齐业务码在日志中的统一输出。

## 一次异常的流程

```text
Service 抛 BusinessException / MVC 参数错误 / 认证过滤器直接拒绝
  → 对应出口确定 HTTP 状态与 Result.code
  → 保存到 request attributes（Servlet）或 exchange attributes（WebFlux）
  → 按原协议返回 Result
  → 访问日志读取属性并输出 status、code 和既有 Trace ID
```

HTTP 状态和业务码是不同维度，例如 status=409、code=SKU_CODE_EXISTS。不能只根据 HTTP 409 推测是编码重复还是乐观锁冲突。

```text
INFO [shop-product] [http-nio-8082-exec-1] [abc123] ... event=HTTP_ACCESS method=POST path=/api/v1/admin/skus status=409 code=SKU_CODE_EXISTS userId=42 durationMs=8 outcome=COMPLETE
```

日志前缀 traceId、Result.traceId、X-Trace-Id 沿用当前请求关联号，不增加新的 Trace ID。HTTP COMPLETE 表示处理链完成，不等于业务成功。

## Servlet 服务

- [ResultCodeContext](../shop-common/src/main/java/org/spring/shopcommon/logging/ResultCodeContext.java) 定义共同属性键，并限制日志业务码格式，防止长文本或换行注入。不依赖 Servlet，网关可以加载。
- [ServletResultCodes](../shop-common/src/main/java/org/spring/shopcommon/logging/ServletResultCodes.java) 将业务码保存到请求属性；无 HTTP 上下文时不创建假请求或线程变量。
- [GlobalExceptionHandler](../shop-common/src/main/java/org/spring/shopcommon/result/GlobalExceptionHandler.java) 记录 BusinessException、DTO 校验错误、JSON/方法等框架错误和未知异常的业务码。5xx 保留一次诊断堆栈，普通业务拒绝不额外刷 WARN。
- 同一个全局 Advice 还实现 ResponseBodyAdvice，在序列化前读取返回的 Java Result，覆盖成功 OK 和直接返回 Result.fail 的情况；它不消费、缓存、解析或重写响应流，返回原对象。
- InternalAuthenticationFilter 的统一 reject() 在 MVC 之前保存 INVALID_INTERNAL_TOKEN 或 FORBIDDEN。因此直连下游等拒绝也有业务码。
- ServletAccessLog 在同步结束或异步 onComplete 时读取原请求属性，输出 status 和 code，不依赖当时的 RequestContextHolder/MDC 业务码字段。

| 场景 | 日志 code |
|---|---|
| 统一成功 Result | OK |
| 商品隐藏或不存在 | PRODUCT_NOT_FOUND |
| 参数校验/非法 JSON | VALIDATION_ERROR |
| HTTP 方法不支持 | METHOD_NOT_ALLOWED |
| SKU 编码重复 | SKU_CODE_EXISTS |
| 版本冲突 | STATE_CONFLICT |
| 内部 JWT 无效 | INVALID_INTERNAL_TOKEN |
| 内部用途/权限拒绝 | FORBIDDEN |
| 数据库等暂时故障 | DEPENDENCY_UNAVAILABLE |
| 未知系统异常 | INTERNAL_ERROR |

未经过统一出口的原生 Servlet 响应使用 HTTP_状态，例如 HTTP_401；该前缀只表示 HTTP 状态，不宣称获知特定业务原因。未处理且逃出过滤链的异常兜底 INTERNAL_ERROR。业务码不放入新响应头，不从外部头读取。

## 网关

GatewayResponses.body() 将同一 code 写入 exchange attributes 和 Result。reject()、认证/权限拒绝、防刷拒绝、统一异常处理均复用该入口。Sentinel 专属回调虽然直接创建 ServerResponse，也调用 body()，因此 RATE_LIMITED 同样被记录。

GatewayAccessLog 输出 status 和 code；外层 ErrorWebExceptionHandler/Sentinel 错误响应仍沿用 phase=headers 的提交回调，普通完成是 phase=complete。日志耗时边界与 30 文档一致。

```text
网关主动拒绝：status=401 code=UNAUTHENTICATED
网关主动拒绝：status=403 code=FORBIDDEN
网关容量拒绝：status=429 code=RATE_LIMITED
网关连接失败：status=503 code=SERVICE_UNAVAILABLE
网关未知异常：status=500 code=INTERNAL_ERROR
```

网关只记录自身生成的业务码。对正常转发的下游响应记录实际 status，code=-；下游的具体业务码记录在下游访问日志，通过 Trace ID 关联。网关不读取响应体，不猜测业务码，不为了日志增加跨服务 HTTP 头。下游 HTTP 200 也不一定等于 Result.code=OK。

网关 5xx 诊断日志也包含 code；未知 500 打印堆栈，已知连接等故障保留原摘要。已经提交的响应不会因日志处理被重写。

## 与 @BizLog 的关系

无需给所有异常添加注解。访问日志捕获最终出口的业务码；@BizLog 继续记录某个操作的 action、bizId、outcome 和原有错误码，切面仍原样抛出异常，不重复打印堆栈。

例如一次商品版本冲突，可以同时有操作摘要 BIZ_OPERATION outcome=REJECTED code=STATE_CONFLICT 和 HTTP_ACCESS status=409 code=STATE_CONFLICT。两者分别描述操作和请求，不是两次异常堆栈。

日志依旧为有界异步输出，满队列可能丢失，不构成可靠审计。本次没有实现数据库审计表、Outbox 或 MQ；没有改动业务接口、POM 继承、application 配置文件或数据库结构。
