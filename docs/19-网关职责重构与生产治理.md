# 网关职责重构与生产治理

日期：2026-10-20，基于当前 Java 17 / Boot 3.2.5 / Gateway 4.1。本文区分已实施的核心重构与建议迁移目录；CORS/转发超时提供已接入测试的配置示例，分布式追踪提供接入方案，未自动添加追踪 SDK 或部署 Collector。

## 1. 当前实现与边界

当前没有 Caffeine 和权限 Pub/Sub。`RbacRedisPublisher` 虽然保留旧名，实际只做受控 Redis 文档写入/CAS；不能据名字推断仍有订阅监听器。用户、角色、权限的有效关联查询及事务失效 outbox 已在 shop-user，网关没有这些业务表访问。

网关承担本地 JWT 验证和 URL/HTTP 方法/路由级权限判断是合理边界。资源是否属于用户、订单状态是否允许操作、金额/库存规则仍由业务服务校验。避免把所有鉴权变成每个请求都调用用户服务：当前热请求读取业务 Redis；只有用户缓存不存在时才在隔离线程通过 Feign 冷加载。

本轮已落地：

| 组件 | 当前职责 |
|---|---|
| [AuthenticationAuthorizationFilter](../shop-gateway/src/main/java/org/spring/shopgateway/auth/AuthenticationAuthorizationFilter.java) | HTTP 适配：清理外部身份、构造用例输入、通过后写可信用户头并转发 |
| [GatewayAccessService](../shop-gateway/src/main/java/org/spring/shopgateway/auth/application/GatewayAccessService.java) | 白名单、Bearer 提取、JWT、权限端口、类型化错误；不接触 exchange/响应/过滤链 |
| [PermissionAuthorizer](../shop-gateway/src/main/java/org/spring/shopgateway/auth/port/PermissionAuthorizer.java) | 纯接口，屏蔽 Redis/Feign/锁实现；false 是无权，异常是依赖/程序失败 |
| [RbacPolicyEvaluator](../shop-gateway/src/main/java/org/spring/shopgateway/auth/policy/RbacPolicyEvaluator.java) | 无 I/O 的规则匹配与 ALL/ANY 权限集合比较 |
| [RbacPermissionCache](../shop-gateway/src/main/java/org/spring/shopgateway/auth/RbacPermissionCache.java) | 实现权限端口，继续沿用 Redis、Redisson 加载锁、epoch 防旧回填和 Feign 隔离机制 |
| [GatewayException](../shop-gateway/src/main/java/org/spring/shopgateway/error/GatewayException.java) | 类型化 401/403/权限依赖 503，固定公开消息，不泄露底层异常内容 |
| [GatewayErrorWebExceptionHandler](../shop-gateway/src/main/java/org/spring/shopgateway/error/GatewayErrorWebExceptionHandler.java) | WebFlux 统一异常出口，复用 Result/GatewayResponses，保留 HTTP 错误语义 |
| [GatewayResponses](../shop-gateway/src/main/java/org/spring/shopgateway/web/GatewayResponses.java) | 统一 JSON 写入、请求 ID、Retry-After；清除旧响应的长度/压缩/缓存验证头 |

JWT 的 RS256/公钥/issuer/audience/时间/sub 校验没有重写；防刷、Sentinel、双 Redis 和现有 POM 继承不变。通用 `shop-cache` 是同步 API，本次没有把它引入 WebFlux 网关。

## 2. 推荐目标目录

以下是逐步迁移的**目标目录**。本轮新增 application、port、policy、error 并拆分职责；现有类暂留原路径，避免一次批量移动破坏配置、测试、文档和 Feign 扫描。

```text
org.spring.shopgateway
├── filter                         # Web/GlobalFilter 的 HTTP 适配器
│   ├── GatewayRequestFilter        # WebFilter：入口可信元信息
│   ├── AuthenticationAuthorizationFilter
│   └── AntiAbuseFilter
├── auth
│   ├── application/GatewayAccessService
│   ├── port
│   │   ├── PermissionAuthorizer
│   │   └── UserPermissionProvider  # 后续拆分缓存读取的端口
│   ├── policy/RbacPolicyEvaluator
│   ├── jwt/JwtIdentityVerifier
│   └── infrastructure/redis
│       ├── RedisPermissionAuthorizer
│       ├── RedisUserPermissionProvider
│       ├── RbacRuleWriter          # 受控写入，替代有歧义的 Publisher 名称
│       └── RbacCodec
├── client/user
│   ├── UserPermissionClient
│   ├── PermissionFeignConfiguration
│   └── FeignUserPermissionLoader   # 仅此处封装阻塞 Feign 的响应式边界
├── protection                     # 防刷策略解析/执行，不承担认证和业务规则
├── web                            # Headers、Path、IP 解析、Responses
├── error                          # 类型化异常和 ErrorWebExceptionHandler
├── config
│   ├── GatewayAuthConfiguration
│   ├── GatewayRedisConfiguration
│   ├── SentinelGatewayConfig
│   └── properties                 # Auth/Redis/Protection 等配置绑定
└── observability                  # 未来可观测性适配，不自己创建第二套请求 UUID
```

后续拆 `RbacPermissionCache` 时，先保持 `PermissionAuthorizer` 不变，再把用户 Redis 读/锁/epoch/回填移入 `RedisUserPermissionProvider`，把同步 Feign 包装移入 `FeignUserPermissionLoader`。规则读取与纯策略比较留在权限适配器。该步骤是后续建议，本轮尚未把缓存和 Feign 的内部方法迁移成这些新类。

建议的依赖方向：`Filter → Application → Port ← Infrastructure`。配置类只负责装配；过滤器不能依赖 Feign、RedisTemplate、RedissonClient 或用户数据库 Mapper。角色管理/权限写事务继续留在用户服务。

## 3. 核心过滤器边界

完整可编译代码见 [AuthenticationAuthorizationFilter](../shop-gateway/src/main/java/org/spring/shopgateway/auth/AuthenticationAuthorizationFilter.java)，核心是：

```java
return access.authorize(request).flatMap(identity -> {
    if (identity.userId() == null) return chain.filter(clean);
    var authenticated = clean.getRequest().mutate()
            .headers(headers -> headers.set(GatewayRequestHeaders.USER_ID, identity.userId()))
            .build();
    return chain.filter(clean.mutate().request(authenticated).build());
});
```

`request` 中只有方法、规范化路径、真实 routeId、入口 requestId 和 Authorization，没有客户端声明的 userId。白名单返回匿名身份；JWT/RBAC 都成功才返回可信 ID。过滤器不捕获 `chain.filter` 的下游异常，因此下游连接失败不会被误判成 JWT 无效或权限 Redis 故障。

GatewayAccessService 在 JWT 范围只把 JwtException 转成 401；在权限端口范围只把已知 Redis/Redisson/Feign/超时/资源拒绝转成权限依赖 503。空权限决策也视为不可用，不能悄悄完成为 200 空响应。无权限是 403；NullPointerException 等程序错误保留 500，便于暴露真实缺陷。

纯策略类不加载数据。没有匹配规则默认拒绝，禁用用户拒绝；多个匹配规则全部满足，单条规则再区分 ALL/ANY。这些只是 URL 入口权限，不替代业务服务的数据归属与交易规则。

## 4. 全局异常与统一响应

完整代码见 [GatewayErrorWebExceptionHandler](../shop-gateway/src/main/java/org/spring/shopgateway/error/GatewayErrorWebExceptionHandler.java)。实现 `ErrorWebExceptionHandler`，不是 MVC 的 `@RestControllerAdvice`。

| 情形 | HTTP | Result.code |
|---|---:|---|
| 缺失/无效 Token | 401 | UNAUTHENTICATED，并附 WWW-Authenticate |
| 权限不足 | 403 | FORBIDDEN |
| Sentinel 容量保护 | 429 | RATE_LIMITED，原有 Sentinel 回调 |
| Redis IP 防刷 | 429 | ABUSE_LIMITED，沿用实际 Retry-After |
| 权限依赖失败 | 503 | AUTHORIZATION_UNAVAILABLE |
| 防刷 Redis 不可用 | 503 | DEPENDENCY_UNAVAILABLE |
| 无服务实例/连接拒绝/DNS 失败 | 503 | SERVICE_UNAVAILABLE |
| 下游响应等待超时 | 504 | UPSTREAM_TIMEOUT |
| 未匹配路由 | 404 | NOT_FOUND |
| 未知程序错误 | 500 | INTERNAL_ERROR |

统一格式继续是：

```json
{"code":"SERVICE_UNAVAILABLE","message":"下游服务暂不可用，请稍后重试","data":null,"traceId":"入口统一关联 ID"}
```

异常处理器的三个边界：

1. 已提交响应直接返回原错误信号，不能再写状态码或追加错误 JSON。SSE/流式下载不能承诺事后改成统一错误正文。
2. Sentinel BlockException 委派给现有专用处理器，不能被未知异常 500 分支截获。
3. 下游正常返回的 400/403/500/502 等 HTTP 响应不是 Reactor 异常，不由该处理器二次包装。否则可能破坏业务错误码、下载或其他协议；业务服务自行遵守统一 Result 契约。

错误响应不输出异常 reason、内部地址、Token、权限文档或堆栈。日志保留请求 ID、状态、异常类别和原因类别。GatewayResponses 清除尚未提交的 Content-Length、Content-Encoding、ETag、Last-Modified，设置 no-store，保留 CORS 和请求 ID 头。

### 三种顺序不能混排

```text
WebFilter：入口 GatewayRequestFilter(-2000)
    → HandlerMapping / 可选 CORS / 路由匹配
    → GlobalFilter：Sentinel(-200) → IP 防刷(-100) → 认证鉴权(-50) → 转发

未处理错误：GatewayErrorWebExceptionHandler(-3)
    → 对 Sentinel BlockException 委派给 Sentinel 专用处理器(-2)
    → Boot 默认错误处理器(-1) 兜底
```

全局异常排序不决定请求过滤器顺序。现有防刷/Sentinel 主动结束响应也继续复用同一个 Result/请求 ID，不要求为了“统一”而强行全部抛异常。

## 5. CORS 集中配置

完整配置见 [application-governance.yml](../shop-gateway/examples/application-governance.yml)，使用当前 Gateway 4.1 的 `spring.cloud.gateway.globalcors`。示例同时设置网关转发连接/响应超时，不改变权限 Feign 的独立超时。

```yaml
spring:
  cloud:
    gateway:
      globalcors:
        add-to-simple-url-handler-mapping: true
        cors-configurations:
          '[/**]':
            allowed-origins: ["${SHOP_FRONTEND_ORIGIN:http://localhost:5173}"]
            allowed-methods: [GET, POST, PUT, PATCH, DELETE, OPTIONS]
            allowed-headers: [Authorization, Content-Type, Accept, Idempotency-Key]
            exposed-headers: [X-Trace-Id, X-Request-Id, Retry-After, Location]
            allow-credentials: false
            max-age: 600
```

按实际前端来源设置 SHOP_FRONTEND_ORIGIN，将示例合并到网关配置，或在以 shop-gateway 为工作目录的 IDE 程序参数中加入 `--spring.config.additional-location=file:./examples/application-governance.yml`。示例未自动合并到主配置，不擅自假定生产域名。

合法浏览器 OPTIONS 预检在 CORS/HandlerMapping 层完成，不需要 JWT，也不转发业务服务；它不是一次业务操作，不能通过把所有 OPTIONS 加入认证白名单代替 CORS 校验。实际 GET/POST 仍经过 Sentinel、防刷和认证。非浏览器调用没有 Origin 时不依赖 CORS，CORS 不能替代身份认证。

当前用 Bearer、不使用跨域 Cookie，因此 allow-credentials=false；如果未来改用 Cookie，必须同时配置精确来源与 CSRF 策略，不能配通配来源。只在网关集中处理 CORS，避免服务端重复产生多个 Access-Control-Allow-Origin。被拒绝的 CORS 请求由 Spring 协议层返回 403，通常没有业务 Result 正文，浏览器也不会向非法来源暴露正文；本轮统一异常格式针对网关处理异常及主动业务拒绝，不声称改写了 CORS 协议处理器。

## 6. 请求 ID 与分布式追踪

2026-10-22 当前实现已更新：入口延续合法 X-Trace-Id 或生成 16 位随机号，exchange、两个头、Result.traceId、Reactor/MDC、Servlet、Feign 及装饰线程池保持同值。完整代码/配置和验证见 [21 文档](21-全链路TraceId与异步上下文.md)。本组件实现跨服务日志关联，尚未接入 Span/Collector。以下是后续完整观测平台的迁移建议。

建议采用 Boot 3 的 Micrometer Tracing + OpenTelemetry/OTLP，通过 W3C traceparent/tracestate 跨进程关联；由 SDK 创建/传播 traceId/spanId，不手工用 UUID 构造 traceparent。升级前需要统一 SDK 与现有 MDC traceId 的归属，避免标准 128 位 Trace ID 与短关联号互相覆盖；不得直接叠加两套同名上下文。

依赖片段：[tracing-dependencies.xml](../shop-gateway/examples/tracing-dependencies.xml)。由当前 Boot/Cloud BOM 管理版本，包含 Actuator、micrometer-tracing-bridge-otel、opentelemetry-exporter-otlp、feign-micrometer；Prometheus 注册器用于指标。不要叠加 Sleuth 或重复使用 Agent/SDK 对同一组件插桩。

配置示例：[application-observability.yml](../shop-gateway/examples/application-observability.yml)。包含 W3C、10% 采样、OTLP Collector 地址、Reactor context-propagation=auto 和 Feign Micrometer 开关。管理端口默认独立 9091/127.0.0.1；Actuator 不经过业务路由 GlobalFilter，不能依赖业务鉴权链保护它。

落地顺序：

1. 在网关和 user 服务添加受 BOM 管理的追踪依赖，部署 OTel Collector 和支持 OTLP 的追踪后端，配置实际 endpoint。
2. 开启 Reactor 自动上下文传播；保留现有 Feign 专用有界 Scheduler，不手工 MDC.put 后跨异步链使用。对之后新增的原生线程池/异步边界单独验证上下文传播。
3. Feign 通过 MicrometerObservationCapability 观察请求；默认 Spring 管理的客户端应保持观测能力，自建客户端不能假定自动具备。现有内部凭据只由 Feign 配置添加，Span 标签不记录凭据或用户权限集合。
4. 分别验证网关服务端 Span、网关路由客户端 Span、Feign 客户端 Span和 user 服务端 Span 的父子关系。只看到网关日志中的一个 traceId，不代表全链路贯通。
5. 先设计现有短关联号与 SDK 标准 traceId 的迁移契约，再统一 Result/两个头/MDC 的关系；不能凭 SDK 新增依赖就假设当前自定义契约自动兼容。

原 2026-10-20 阶段未启用完整追踪 SDK/导出/Collector；2026-10-22 已安装轻量 context-propagation 桥接库并验证自定义日志关联链路，仍未部署完整观测后端。
