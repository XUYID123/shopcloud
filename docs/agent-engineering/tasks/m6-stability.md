# M6 稳定性与扩容

2026-11-24 · ROUTE-05 / ROUTE-10 · COMPLEX / HIGH

## 范围与设计审查

本阶段以[实施与验收](../../04-实施与验收.md)为准。复用商品缓存、共享 Redis 防刷、Sentinel 网关适配器、Nacos 发现、交易 Outbox/Inbox 与现有状态机。在隔离环境执行复验。设计容量的硬件、数据集和稳态时长单独记录。

| 评估项 | 判断 |
| --- | --- |
| 流控、配置与实例发现 | REQUIRED。保持网关单实例容量规则，启用后从 Nacos 读取并验证持久化阈值。订单全局模式由独立 Sentinel Token Server 发放配额，客户端失败时拒绝新下单，已提交幂等重放仍能查询。不用流控代替资源状态校验。 |
| MySQL、事务与并发 | REQUIRED。继续用 Outbox 行租约和 Inbox 持久幂等。并行投递有固定上限，发送仍在事务外。用只读对账识别积压和滞留状态，备份恢复只在隔离库演练。 |
| RocketMQ | REQUIRED。保留现有 Topic、Tag、Group、版本和事件 ID。消费失败继续交给 Broker 重投及死信，恢复操作有对账证据并保留原事件标识。 |
| Redis | REQUIRED 验证。复用业务缓存和安全实例，保持安全拒绝与有界缓存回源的已有语义。 |
| 权限、日志与测试 | REQUIRED。运维脚本使用独立权限和可审核的数据范围。限制指标维度和日志内容，不记录消息正文、私钥或订单个人信息。压测与故障演练限隔离环境。 |

## 交付与运行

- [运行说明](../../../infra/stability/README.md)包含三节点 Nacos、Token Server、规则发布、Outbox 调优、告警指标、安全重放和恢复演练。
- [容量场景](../../../performance/README.md)包含 k6 商品读、下单及热点库存场景。容量采用独立测量阶段，报告启动率、受理和完成延迟、拒绝及掉迭代。
- 默认沿用现有服务名和限流语义。Nacos 持久化规则、集群限额与结算熔断需要按环境启用。Outbox 保持原有投递和消费契约，独立线程保留原批量与租约算法，可按连接池预算增加并发。

## 验证

- 使用 Java 17 通过 52 项相关 Maven 测试。覆盖 M3–M5 相关业务代码、网关路由、权限与 Scoped JWT、非法规则拒绝、结算依赖熔断及半开恢复，以及退避上限。日志位于 `shop-order/target/m6-isolated-tests.log` 和 `shop-order/target/m6-retry-package.log`。
- 使用 `python -X utf8 infra/quality/gate.py lint`、Python 语法检查、Node 语法检查和 k6 `inspect` 验证文档与脚本。
- 第一轮双副本发现 Sentinel SDK 的请求编码器在首笔业务调用时才初始化。将初始化移到 Token 客户端建立之前，修复从未处理过报价的实例收到下单时的拒绝。
- Maven 打包通过。订单 Boot JAR 包含独立 Token Server 入口、Nacos 3.1.1 客户端和 Sentinel 1.8.9 集群客户端与服务端。
- Nacos 3.2.4 三节点均可发现两个订单副本；默认 namespace 看不到演练实例；暂停一节点后仍可发现和读取商品。真实网关复验从报价到 `COMPLETED`。
- 复验 Nacos 阈值热更新、无效配置保留上一次阈值和缺关键规则拒绝启动。网关各实例执行自己的容量规则；将全局订单额度设为 3，同一脉冲在两个订单副本合计通过 3 次，超限返回 429 和 `Retry-After`。停止 Token Server 时新下单返回 503，已完成订单可按原幂等键返回；重启后从 Nacos 恢复并继续受理。
- 暂停安全 Redis 时网关返回 503，暂停业务缓存 Redis 时商品详情仍可从数据库读取。两个实例恢复后再次通过网关验证。
- 首次 60 秒 RocketMQ Proxy 故障演练中，原退避在 Broker 恢复阶段产生 64 秒等待，预占重试和 120 秒准备超时相撞。收紧长退避至 16–19 秒，保留超时关单和释放的业务机制。用新增单元测试验证上限与事件分散。
- RocketMQ 5.5.1 Proxy 复验停机 60 秒。订单一直保留待发送记录，Proxy 重启后 49.45 秒到 `UNPAID`，核对仅预占两袋。从同一发件箱用原事件 ID 再投递后，仍只有两袋预占及一条 Inbox 收据。日志位于 `shop-order/target/m6-broker-verified.log`。
- 用独立 Topic 和消费组验证永久失败。Broker 按组配置重试一次，第二次失败后在对应 DLQ 查到原事件键，见 `shop-order/target/m6-dlq-run.log`。
- 在独立 MySQL 8.4.11 应用订单、库存和支付迁移。三个库均能输出健康指标，故意写入超时准备与履约不一致夹具时返回告警。将合成订单、物流及其批次快照备份后恢复到空库，表计数与业务 SHA-256 摘要一致。日志为 `shop-order/target/m6-ops-run.log`。

## 本机容量样本

网关与订单各两个 JVM 副本，单 JVM 堆上限 512 MiB。Windows 回环发压，Docker VM 有 16 个逻辑 CPU 和约 11.6 GiB 内存，运行 MySQL 8.4.11、Redis 8.2.10、RocketMQ 5.5.1。演练使用合成商品和订单。

| 场景 | 本机样本 |
| --- | --- |
| 商品详情与列表 | 约 30 RPS，持续 10 秒。301 个请求均成功。P95 62.36 ms、P99 84.17 ms，无掉迭代。 |
| 下单 | 约 2 RPS，4 笔全部预占成功。下单受理 P95 162.47 ms，库存预占最终完成 P95 504.15 ms，无掉迭代。 |
| Mock 支付 | 2 笔均到 `PAID / CONFIRMED`，从触发支付事件到确认的样本约 1 秒。 |
| 单 SKU 竞争 | 4 个并行订单争用 2 袋，2 笔成功预占、2 笔缺货拒绝。数据库为可用 0、预占 2、已扣 0。 |

k6 1.3.0 输出位于 `shop-order/target/m6-k6-catalog.log`、`m6-k6-order-verified.log`、`m6-k6-payment-verified.log` 和 `m6-k6-stock.log`。期间使用的临时服务、容器、测试卷、备份文件与凭据已清理。

## 验收边界

目标规模的 2,000 RPS 商品读取、200 RPS 下单及 15 分钟稳态负载需要目标硬件、测试数据集和隔离副本拓扑。正式环境的告警接收、数据库及消息高可用继续按[实施计划](../../04-实施与验收.md)验收。全局配额使用一个活动 Token Server，其故障期间拒绝新下单。长期死信和支付异常由运维查证后处置。
