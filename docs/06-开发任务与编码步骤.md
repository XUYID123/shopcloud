# 开发任务与编码步骤

编制日期：2026-10-15。状态：阶段开发清单；用户注册与 Docker/Flyway 已实现，具体代码及验收见 08/09 文档，其余任务按阶段完成。业务字段、接口及状态机以 `02-业务与数据设计.md`、`03-接口文档.md` 和 `openapi.json` 为准。

## 1. 第一个交付目标

使用已经存在的 shop-user，先实现用户注册，再完成登录、当前用户查询、刷新与退出。从 IDE 启动用户服务与网关，用户服务注册到 Nacos；消费者通过网关访问用户接口；Sentinel 规则从 Nacos 加载，超限返回 HTTP 429。商品查询安排在用户认证之后。

首轮使用 MySQL、Nacos、Sentinel Dashboard、shop-user、shop-gateway；登录会话阶段加入 Redis。shop-user 目前已有启动类、测试类和应用名配置，还没有业务 Java 类或建表 SQL。直接在现有模块中补全业务，不重新创建用户服务。

## 2. 当前工程需要先处理的问题

| 当前发现 | 开发任务 | 完成依据 |
|---|---|---|
| shop-user 的 artifactId 是 shop-common | 改为 shop-user | Maven 聚合构建没有重复模块坐标 |
| 根项目使用 JDK 17 / Boot 3.2.5，多个子模块单独使用 Boot 4.1.1；文档目标为 JDK 21 / Boot 4.0.x | 按架构文档统一 JDK、父 POM、BOM、编译及构建插件版本 | IDE 与命令行使用相同 JDK，依赖解析及集成启动通过 |
| 根 POM 只登记两个模块 | 登记本阶段参与构建的模块，其他模块实施时登记 | 从根项目可以编译已实施模块 |
| common 同时包含启动类、测试接口、Web starter、MySQL 驱动和 Compose 集成 | common 改为普通 JAR；测试接口迁至业务模块或移除，基础设施配置统一到 infra | common 能作为依赖被引用，无独立启动进程 |
| 各服务使用 org.spring 包名，包之间互为兄弟 | 实施时统一为 com.dong.shop.<业务>，显式处理公共组件的注册 | 公共异常处理器实际生效，不因组件扫描范围失效 |
| MySQL 使用 latest，端口动态映射 | infra 固定镜像版本、开发端口、健康检查和数据卷，提供环境变量示例 | 重启保留数据，IDE 能稳定连接本机映射端口 |
| 当前异常处理总是返回普通对象，并把异常原文拼给客户端 | 区分 HTTP 状态及业务码，服务端记录完整异常 | 不存在返回 404、参数错误返回 400、未知错误返回 500；客户端不暴露异常细节 |

版本采用现有架构文档的目标分支；补丁组合仍须真实验证后锁定。Alibaba 官方矩阵明确 2025.1.x 对应 Boot 4.0.x / Cloud 2025.1.x，因此不能直接沿用各模块的独立 Boot 4.1.1 parent。本文没有重新选择一套版本，也不把依赖解析视为集成成功。[官方版本矩阵](https://sca.aliyun.com/en/docs/2025.x/overview/version-explain/)

此前关闭 common 的自动 Compose 是排除现有脚手架故障的临时处理；正式开发时 common 是公共库。IDE 启动业务服务，Compose 单独管理基础设施。

## 3. 按顺序实现第一轮

### 步骤 1：统一 Maven 工程

1. 修正 shop-user 坐标，统一业务模块的 parent、groupId、版本属性与插件。
2. 按第 2 节目标把 shop-common 调整为普通依赖库。
3. 先将 common、user、gateway 纳入一致的构建；商品、订单、库存、支付模块实施时采用同一规则。
4. 本项目购物车归属 shop-order，暂不启用现有 shop-cart 空壳。现有 shop-pay 对应设计中的 shop-payment，实施支付时统一目录、artifactId、应用名、配置及路由命名。
5. 验证根项目构建、业务模块打包和 IDE 启动；不要只验证某个 main 方法。

验收：没有重复 Maven 坐标，业务模块没有独立覆盖框架版本，common 可以被 user 引用。

### 步骤 2：先写公共响应和异常代码

这是工程结构修正后的第一组 Java 代码，保持当前 Result 类的名称，逐项完善，不另造重复响应类。

| 所属模块 | 类 | 职责 |
|---|---|---|
| common | result/Result<T> | 统一 code、message、data、traceId；code 与接口契约一致，使用字符串 |
| common | result/PageResult<T> | 商品列表阶段增加，包含 items、page、size、total |
| common | exception/ErrorCode | 通用错误码，例如 VALIDATION_ERROR、NOT_FOUND、INTERNAL_ERROR |
| common | exception/BusinessException | 携带业务错误码，表示可预期的业务拒绝 |
| common | result/GlobalExceptionHandler | 共享 MVC 异常处理器，将异常映射为实际 HTTP 400/401/403/404/409/500；由 common 自动配置注册 |
| user | web/RequestIdFilter | 校验或生成请求标识，写入响应头与 MDC，结束后清理 |
| gateway | 网关请求标识及错误处理配置 | 使用 WebFlux 对应机制，传播请求标识，处理网关错误与 Sentinel 拒绝 |

common 统一提供响应、分页、错误码、业务异常和共享 MVC 全局异常处理器。处理器保留在 common，不复制到各业务服务；common 内提供 @AutoConfiguration、条件化 @Bean 和 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports，使 MVC 服务添加依赖即可启用。引用普通 JAR 本身不代表其组件自动进入扫描范围。common 所需 Web 依赖设置 optional，业务服务声明自己的 MVC starter；WebFlux 网关复用响应与错误码，使用对应的响应式异常机制，该 MVC 配置不在响应式环境启用。请求标识 Filter 后续也可按相同方式提供公共配置。具体操作见 07 手册。

验收：成功 code=OK；未知资源 HTTP 404；参数错误 HTTP 400；未知异常 HTTP 500 且只返回通用提示；错误体含 traceId，可对应服务端日志。

### 步骤 3：搭建基础设施并接入 Nacos

1. 在 infra 保存 Compose 与环境变量示例，单独启动 MySQL、Nacos、Sentinel Dashboard；会话阶段加入 Redis。
2. 创建开发 namespace、配置 Group、应用配置及 Sentinel 规则，按 05 文档配置客户端和网络端口。
3. user 使用 8081，gateway 使用 8080；用户数据库账号只访问 flour_user。
4. 配置应用名、Nacos Discovery/Config、显式配置导入、Actuator 探针及数据库连接超时。
5. 启动时检查服务注册、关键配置加载、规则订阅；缺少关键配置或规则不对外就绪。

验收：Nacos 可看到实例；非秘密演示配置受控刷新；服务启动日志能够定位配置来源。Sentinel Dashboard 有监控连接不等于限流规则已生效。

### 步骤 4：第一条业务只做用户注册

先写 Flyway 建表迁移，用户表字段和约束以 02 文档为准，包括 ID、用户名、密码哈希、角色、账号状态与时间。用户名建立数据库唯一约束，明确大小写比较规则。

实现 POST /api/v1/users，输入 username、password。用户名 3–32 位字母/数字/下划线，密码遵守现有接口契约的 8–72 位 ASCII 可打印非空白字符约束；角色由服务端设置为 USER，客户端不能指定 ADMIN。

密码使用 BCrypt 哈希保存，不记录请求密码日志，不保存明文密码，不向客户端返回密码或哈希。提前查询用户名可提供友好提示，但必须捕获数据库唯一约束冲突，保证并发重复注册也返回 HTTP 409。

验收：合法注册 HTTP 201，data 仅含契约规定的 userId、username、roles；参数错误 HTTP 400；重复用户名 HTTP 409；用户与 USER 角色关联原子提交，密码为哈希。注册实现见 09 文档。

### 步骤 5：从数据库向接口逐层实现

采用简单分层，先按如下顺序写代码：

1. resources/db/migration/V1__create_user_table.sql：用户表、用户名唯一约束及必要索引。
2. entity/UserEntity：数据库映射，包含 passwordHash；不直接作为接口响应。
3. mapper/UserMapper 与 SQL：按用户名查找、插入用户、按 ID 查询。
4. dto/UserRegisterRequest 与 vo/UserVO：校验输入，只输出契约允许的用户信息。
5. service/UserService：注册规则、BCrypt 编码、默认角色与唯一冲突处理。
6. controller/UserController：接收 POST /api/v1/users，返回 HTTP 201、Location 与统一响应。
7. 测试：合法/非法注册、角色注入、敏感字段泄露、真实 MySQL 下的并发重复用户名。

如果某个简单查询无需独立接口与实现类，就保留一个 service 类，避免为每层堆叠没有行为的空类。

注册通过后依次补齐认证接口：

| 方法 | 路径 | 要实现的内容 |
|---|---|---|
| POST | /api/v1/users | 注册，HTTP 201 |
| POST | /api/v1/auth/sessions | 校验用户名和密码，创建会话并签发凭证，HTTP 201 |
| GET | /api/v1/users/me | 从已验证身份读取当前用户，HTTP 200 |
| GET | /api/v1/auth/sessions/current | 查询当前登录会话，HTTP 200 |
| POST | /api/v1/auth/token-refreshes | 刷新并轮换凭证，HTTP 200 |
| DELETE | /api/v1/auth/sessions/current | 撤销当前会话，HTTP 200 |

登录阶段落实 Spring Security、非对称 JWT、Redis 会话状态、刷新轮换与退出撤销。网关和下游服务都验证凭证与会话，不能信任客户端传来的 X-User-Id。退出后旧 token 被拒绝；旧刷新凭证不能再次消费；账号不存在与密码错误返回一致提示。签名密钥外部注入，不能提交到仓库。具体会话字段、期限及状态按 02/03 文档实现。

### 步骤 6：打通 Gateway 与 Sentinel

1. 网关使用 lb://shop-user 通过 Nacos 发现实例，注册和登录公开，其余接口按契约鉴权；不配置内部接口透传。
2. 传播请求标识，验证从网关响应可以追踪到用户服务日志。
3. 网关接入 Sentinel Gateway Adapter，用户服务接入业务资源保护，规则分别使用对应类型；注册和登录配置入口保护，账号/IP 防刷按用户阶段实现。
4. 演示时将测试资源阈值设置为低值，例如每实例 5 QPS，便于观察；这只是功能验证参数，不是容量目标。
5. 规则从 Nacos 持久化源加载，超限实际返回 HTTP 429、Retry-After 和 RATE_LIMITED；重启应用验证规则恢复。
6. 用可控的依赖超时/失败场景验证 Sentinel 熔断与半开恢复，返回 HTTP 503，不用伪造空商品列表表示成功。

验收：通过 8080 完成注册、登录和当前用户查询；关闭一个用户实例时可发现状态变化；两个实例共享会话状态并能参与调用；流控、熔断和规则恢复都有实际证据。内部数据源故障返回明确错误，不能泄露 JDBC 异常。

## 4. 后续业务顺序

| 顺序 | 模块 | 核心开发内容 | 阶段验收 |
|---|---|---|---|

| 3 | order | 购物车绝对数量更新、商品/地址复核、重量运费、5 分钟报价 | 2 袋 5kg 高筋粉：商品 6400 分、运费 1000 分、应付 7400 分 |
| 4 | order + 新增 inventory + RabbitMQ | 下单幂等、PREPARING、Outbox、批次库存预占、消费去重、预占结果回传 | 同一幂等键只有一单；多 SKU 预占原子化；不足不留部分库存占用 |
| 5 | payment + order + inventory | 模拟支付、验签/金额校验、支付与关单控制、库存确认/释放、取消/超时、查单及异常退款 | 支付/取消竞争、重复回调、乱序消息可恢复，收款与库存均可对账 |
| 6 | order | 管理员发货、批次质量/有效期检查、物流记录、用户收货 | 交易走到 COMPLETED，重复发货/收货没有重复副作用 |
| 7 | 各服务 | Redis 缓存/防刷、多实例、监控、故障演练、压测及容量调整 | 真实并发与故障测试报告，按 04 文档验收 |

商品阶段先写 category、product_spu、product_sku 的迁移，再按 Entity → Mapper → DTO/VO → Service → Controller 实现 GET /api/v1/categories、GET /api/v1/products、GET /api/v1/products/{productId}、GET /api/v1/skus/{skuId}。金额为整数分，重量为整数克；分页 size 上限 50，排序采用白名单；下架商品和停用规格不可公开查询。库存归库存服务，在该阶段前 estimatedAvailable 返回 null，现有契约允许未知值。

Nacos 和 Sentinel 从首轮接入；Outbox、幂等、库存条件更新和补偿从交易代码开始实现。Redis 会话及防刷在用户阶段加入，商品缓存优化稍后加入。首轮演示可完全使用接口工具，页面在业务链路稳定后加入。

## 5. 每次写代码的工作方式

一次只完成一个可验收任务：确认接口输入输出 → 迁移/约束 → 数据访问 → 业务规则 → HTTP 接口 → 正常和关键异常验证 → 更新实现状态。

第一张任务卡就是“修正 Maven 坐标与 common 职责”；完成后写 Result、ErrorCode、BusinessException，再在现有 shop-user 中实现用户注册。不要把测试接口启动成功当成商城功能完成，也不要把第一轮限流演示当成高并发容量证明。
