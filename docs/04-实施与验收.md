# 实施顺序与验收

## 1. 可交付阶段

每一步先跑通再扩展。预计节奏随 Java/Spring 熟练度变化；按阶段验收，不用日期承诺替代功能质量。

| 阶段 | 实现任务 | 完成标准 |
|---|---|---|
| M0 工程与环境 | 修正 shop-user 坐标；统一 JDK 21/Boot 4.0.8/Cloud 2025.1.3/Alibaba 2025.1.0.0；common 普通库；网关/业务模块；Compose 部署 Nacos 3.2.4 与 Sentinel 1.8.9；初始化 namespace/config/规则；MySQL 分库分账号；RESTful 契约、异常、日志、迁移、探针 | 模块可打包启动；Nacos 注册发现与配置刷新正常；Sentinel 规则加载、流控/熔断生效；网关路由和探针正常；镜像/依赖锁定，无 latest/明文生产口令 |
| M1 用户与商品 | 用户密码/会话/地址/RBAC；分类/SPU/SKU/上架；演示管理员/用户/商品数据 | 登录、退出、地址归属和后台权限正确；商品可浏览，SKU 可售状态正确 |
| M2 购物车与结算 | 购物车绝对数量、地址/价格复核、重量和运费规则、quote 5 分钟有效 | 2 袋 5kg 示例结算 7400 分；改价、报价过期、不支持地区被拒绝 |
| M3 下单与库存 | 订单 PREPARING、本地 Outbox；批次库存、FEFO、多 SKU 本地事务、消费幂等、反悬挂墓碑；订单状态查询 | 重复下单只一个订单；只有真实预占成功才 UNPAID；库存不足最终 FAILED；不超卖 |
| M4 支付与关闭 | Mock 适配器、签名回调、支付控制记录、查单/关单、Confirm/Release、异常全额退款、超时扫描 | 正常支付最终 PAID/CONFIRMED；取消/超时最终 CLOSED/RELEASED；竞争与未知结果可恢复 |
| M5 履约与联调 | 管理查询/物流/发货、批次追溯、用户确认收货；简单消费者与管理页面或完整接口演示 | 完整交易到 COMPLETED；冻结/过期批次禁止发货；越权访问失败 |
| M6 稳定性与扩容 | Redis 缓存/防刷、Nacos 集群与多实例、Sentinel 规则持久化/恢复/集群流控、重试/DLQ、监控告警、备份恢复、k6/故障注入 | 下表业务与容量验收有实测报告；全局限流与单实例限流口径分别验证；所有中间状态有恢复任务 |

消息可靠性不是最后临时加的优化：Outbox 与幂等要在 M3 开始实现。M6 主要验证故障和容量，不应补写整个一致性设计。

建议目录：

```text
springcloud-demo/
  pom.xml
  shop-common/           # 普通公共库
  shop-contracts/        # 可选，版本化 HTTP DTO/事件
  shop-gateway/
  shop-user/
  shop-product/
  shop-inventory/
  shop-order/
  shop-payment/
  infra/                # Compose、观测配置、环境变量示例
    nacos/              # namespace、初始化配置、配置备份与数据库迁移
    sentinel/           # Dashboard、规则模板、按需 Token Server
  docs/
  performance/          # k6 场景和容量报告
  web/                  # Vue 消费者/管理页面，M5 加入
```

每个业务模块自己的 `resources/db/migration` 保存 Flyway SQL。包名统一为 `com.dong.shop.<业务>`，业务内按 controller/application/domain/infrastructure 分层即可，不把小项目拆成大量空模块。

## 3. 必须通过的业务验收

| 场景 | 预期证据 |
|---|---|
| 正常交易 | 结算金额正确，UNPAID → PAID/CONFIRMED → SHIPPED → COMPLETED；订单含价格/地址/批次快照 |
| 同一幂等键并发下单 100 次 | 只有一个订单、一份预占；相同 key 换内容 409；不同 key 使用同 quote 不重复下单 |
| 库存 100 袋，1,000 次独立订单每单 1 袋 | 恰有 100 份有效预占，其余明确失败；所有数量非负；不把重复 key 混进库存竞争测试 |
| 多 SKU 一项缺货 | 不留下其他 SKU 的部分预占；订单 FAILED |
| 两个有效批次 + 一个过期批次 | 先分配最早到期有效批次；过期/冻结不参与新预占 |
| 调价、下架、报价过期 | 新订单被明确拒绝或按已复核快照成交；已受理订单价格不被后台改写 |
| 越权/伪造身份 | 他人地址/订单/支付返回 404；USER 管理接口 403；伪造 X-User-Id 不起作用 |
| 重复支付/回调 | 一个支付事实，只确认一次库存；正确重复回调 ACK，错误金额/签名/商户不入账 |
| 正常取消与超时 | CLOSING 经渠道关单确认再 CLOSED/RELEASED；不能先释放库存 |
| 支付与超时并发 | 已付则最终 PAID/CONFIRMED，已关则 CLOSED/RELEASED；关闭后异常收款最终 REFUNDED，不出现收款无订单处理记录 |
| 释放消息先到、预占消息后到 | RELEASED 墓碑阻止晚到预占，无悬挂库存 |
| 关闭先到、创建支付后到 | CLOSED 墓碑阻止晚到创建；create-in-flight 必须查证，不能在未知时释放 |
| MQ 停机 / 服务在提交或 ACK 前后崩溃 | 订单意图不丢失；恢复后 Outbox/去重完成；重复事件不重复扣库或退款 |
| Redis 停机 | 商品有界回源不压垮 DB；不能绕过鉴权/限流；敏感请求明确 503 或权威检查 |
| 批次冻结/过期发生在支付之后 | 发货被阻断；异常进入查证/补偿记录，无自动跳过批次检查 |
| 发货/收货重复 | 一个 shipment、一次状态迁移；未支付/未确认库存不能发货 |
| 刷新/退出 | 轮换后旧 refresh 不能新签发；退出的会话被撤销，多个服务一致拒绝旧 token |
| RESTful 契约 | 资源路径无业务动作动词；注册创建 users、登录创建 sessions、退出 DELETE session；取消申请 202 + 可查询 Location；PUT 收货幂等；GET 无写副作用 |
| Nacos 注册与隔离 | 网关/业务实例注册到同一环境 namespace/group；两副本可发现；dev/test/prod 配置与服务列表互不串用 |
| Nacos 刷新与故障 | 非秘密参数受控刷新；非法配置拒绝并保留有效版本；已有实例使用最后有效值，新实例缺少关键配置/规则不得就绪 |
| Sentinel 流控与熔断 | 超阈值返回 429 + Retry-After；慢/失败依赖触发熔断返回 503；半开恢复正常；下单/支付不 fallback 成成功 |
| Sentinel 规则恢复 | 修改 Nacos 规则后生效；应用重启从持久化源恢复；Dashboard 停机不影响本地执行；只在 Dashboard 点规则不算持久化验收 |
| Sentinel 多实例与集群 | 本地规则按实例统计；全局 order.create 规则使用 Token Server 在两副本联合压测；Token Server 故障策略有界且可观测 |

为关闭竞争、重复/乱序消息、提交后崩溃编写集成测试；使用真实数据库唯一约束与行锁，不能只靠内存 mock 测出“不超卖”。测试结束后对账订单、reservation、库存流水、支付/退款记录。

## 4. 容量验收方法

以下数字是项目目标，不是选型后的性能保证。基准环境建议：应用总预算 16 vCPU / 32 GB（网关 2 副本、订单/库存/支付至少 2 副本，其余按负载配置），MySQL 独立 8 vCPU / 16 GB + SSD，Redis 独立 2 vCPU / 4 GB，RabbitMQ 三节点各 2 vCPU / 4 GB，同地域内网；压测机另部署。完整记录版本、磁盘、网络、副本与连接池，不能与学习笔记本直接比较。

数据集：约 1 万 SKU，足量未过期库存，约 10 万历史订单，至少 1 万测试用户；商品 ID 热点分布约 80/20。购买目标场景库存充分，缺货场景另测。为压测生成独立报价和幂等键；每用户活跃订单≤5，通过支付/关闭消费者清理，避免限额先成为瓶颈。

容量测试时将 Sentinel 准入阈值设为高于目标负载的安全值（例如下单全局 250 RPS），另设场景验证 200 RPS 限流规则；不能用被限流拒绝的请求证明业务处理能力。记录 Nacos/Sentinel/Token Server 的版本、规则快照及额外资源预算；Nacos 三节点、Dashboard 和 Token Server 不占用上述业务应用预算。

| 场景 | 目标与统计口径 |
|---|---|
| 商品详情/列表命中缓存 | 2,000 RPS 持续 15 分钟，缓存命中≥95%，P95≤200 ms，P99≤500 ms，意外错误<0.1% |
| 下单受理 | 200 RPS 持续 15 分钟，POST P95≤500 ms、P99≤1 s；仅统计库存充分且合法请求，202 为受理，不能算最终成功 |
| 库存预占最终完成 | 正常 MQ 下 PREPARING → UNPAID P95≤2 s、P99≤5 s，积压不能随测试持续线性增长；记录最终失败率 |
| 完整支付与履约准备 | 正常 Mock 回调到 PAID/CONFIRMED P95≤3 s；重复回调无重复副作用 |
| 单热点 SKU 竞争 | 100 袋、1,000 请求，验证不超卖，并记录吞吐/锁等待；不承诺可按普通多 SKU 场景线性扩容 |
| 故障恢复 | MQ 暂停 60 秒后恢复，记录 Outbox 与中间状态恢复时间；无孤儿库存/未处理收款，积压消退目标≤5 分钟 |

暖机 5 分钟 → 逐级升压 → 稳态 15 分钟 → 检查资源与对账。先分别测读/写，再混合测业务；记录有意的 409/422/429 与意外 5xx，拒绝率不能藏进“成功率”。接口受理延迟、最终完成延迟、端到端成功比例分别报告。

超过目标后先定位数据库锁/连接池、队列最老消息、商品报价调用、网关并发与认证状态检查；按瓶颈调整。单节点 Compose 只用于功能演示，不用于证明生产高可用或以上容量。

## 5. 进入真实经营前的完成项

1. 接入实际支付渠道的签名/解密/证书、支付/关单/查单/退款/退款查单、日对账，经过沙箱和异常资金流程验收。
2. 将示例价格、商品标签、配送地区及运费替换为经营方核验的实际资料；真实消费者售后、退款与客服流程补齐。
3. HTTPS、秘密管理、管理员账号/权限、脱敏、审计、安全基线、依赖维护与漏洞修复落实。
4. 数据库高可用、RabbitMQ quorum、Redis 高可用、Nacos 集群、Sentinel 持久化规则及全局限流故障策略、健康探针、告警接收人、备份与恢复演练、发布回滚完成。
5. 完成目标硬件上容量实测，保留容量余量，明确降级与故障处理责任人。

当前交付为方案和契约，尚无可运行商城、支付集成或性能实测结果。
